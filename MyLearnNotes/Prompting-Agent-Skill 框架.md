> 学习方式：知识点拆解 → 问答检验 → 逐题反馈 → 学习总结
> 正确率：72%（36/50）

---

## 一、知识点大纲

### 📌 核心知识点

1. **Prompting、Agent、Skill 三层递进关系**——从"临时指令"到"角色固化"再到"可复用的标准化操作手册"
2. **Skill 的核心承诺是「一致性」，不是「正确性」**——保证每次执行方法一样，不保证结果一定对
3. **Agent 与 Skill 的调用关系是"多对多"复用**——一个 Agent 可调用多个 Skill，一个 Skill 也可被多个 Agent 复用，二者是独立文件、按需触发，而非内容合并
4. **Skill 的真实文件架构与渐进式加载（progressive disclosure）机制**——通过分层文件结构实现按需读取，节省 token
5. **description 字段的语义匹配触发机制**——Claude 依据 description 自动判断是否激活对应 Agent/Skill，而非手动显式调用
6. **确定性脚本化的边界**——任务能否用脚本代替 LLM 自由推理，取决于输入输出空间是否"有限可枚举"

### 🔑 关键概念/术语

| 术语                                | 解释                                                                                  |
| --------------------------------- | ----------------------------------------------------------------------------------- |
| **Prompting**                     | 一次性、临时性的自然语言指令，无持久化、无复用性                                                            |
| **Agent**                         | 角色/岗位定义，声明"我是谁、我会用哪些能力"，本身不规定具体执行细节                                                 |
| **Skill**                         | 标准化操作手册，规定具体执行步骤、格式、脚本调用方式，是"一致性"的真正载体                                              |
| **SKILL.md**                      | Skill 的核心文件，仅存放任务描述、步骤、预期结果（元数据级别，省 token）                                          |
| **progressive disclosure（渐进式加载）** | Claude 平时只读取 SKILL.md 摘要，真正执行时才加载 `scripts/`，需要格式参考时才读 `examples.md`/`reference.md` |
| **description 语义匹配**              | Agent/Skill 是否被自动激活，取决于 description 与用户请求的语义相似度，而非手动调用命令                            |
| **一致性 vs 正确性**                    | 一致性 = 每次执行路径/方法相同；正确性 = 结果是否符合事实。Skill 只解决前者                                        |

### ⚠️ 难点/易混淆点

1. **Agent 与 Skill 关系的误解**：容易误认为 Skill 内容会被"合并"进 Agent 定义里，实际上二者是**独立文件**，靠 description 匹配**按需触发**
2. **"写了规则约束 = 结果一定稳定"的误区**：即使在 SKILL.md 里写明"按XX标准执行"（如引用 CVSS），只要中间步骤仍依赖 LLM **开放式自由推理**（比如给一个漏洞打1-10分），结果依然会因采样随机性而波动。文字约束消除不了推理层面的不确定性
3. **确定性脚本化的边界判断**：并非"能写规则就能脚本化"。真正可脚本化的是**输入输出空间有限可枚举**的任务（如字段匹配、公式计算）；涉及**理解上下文语义**的判断（如"这个文件类型在当前环境下能否被解析执行"）天然无法穷举规则，只能靠 LLM 判断——但可以把"开放判断"**拆解成有限选项的窄问题**，再用脚本聚合结果，从而降低波动

### 第3题｜技术设计题（Skill 文件架构）

**题目**：以 `stock-agent` 为例，设计一套调用股票数据的 Agent + Skill 文件架构。

**我的回答**：

```
.claude/agents/stock-agent.md          # Agent：角色定义
.claude/skill/stock-fetcher/
  ├── SKILL.md                          # 核心：任务+步骤+预期结果
  ├── scripts/                          # 可执行脚本（python + api key/cookie）
  ├── examples.md                       # 返回示例
  └── reference.md                      # 参考格式/补充文档
```

并指出：description 需明确写触发关键词。

**反馈：✅ 正确，10/10（加分项）**

- 完全对应官方真实的"渐进式加载"分层设计（SKILL.md 摘要 + scripts 可执行代码 + examples/reference 补充说明）
- 🔧 **小纠正**：目录应为 `.claude/skills/`（复数），而非 `.claude/skill/`（单数），否则 Claude 可能无法识别
- **补充**：description 决定的是**语义自动匹配触发**，不是手动显式调用 `/stock-fetcher`，这是整套机制自动生效的关键

### 第4题｜场景应用+难点分析题

**题目**：`code-review-agent` 的 SKILL.md 步骤稳定，但同一段代码 3 次测试的"漏洞严重等级评分"不一致（一次高危、一次中危）。

1. 违反了框架里哪一层承诺？为什么？
2. 如何修改 SKILL.md 让评分稳定？

**我的回答**：

1. 违反了 Agent 的一致性承诺，原因是 SKILL.md 没有明确漏洞等级的评估方法、步骤和标准
2. 加上约束，例如按照 CVSS 3.1 评估漏洞等级并给出 CVSS 评分

**反馈：🟡 部分正确，7/10**

- ✔️ 定位问题原因正确（评分步骤缺乏标准，退化为自由推理）
- ✔️ 引入 CVSS 方向正确
- ❌ **更精确的说法**：应是 **Skill 层面覆盖不完整**，而非笼统说"Agent 的一致性承诺"——Agent 只声明用哪个 Skill，一致性由 Skill 兑现
- ❌ **深层原因遗漏**：即使写"按CVSS标准评分"，由于评分子维度（攻击复杂度、影响范围等）本质仍是 LLM 的**开放式主观判断**，采样随机性依然会导致结果波动。文字约束≠确定性结果
- **完整修复方案**：把"评分"环节从"LLM自由推理"改造成"确定性计算"——① 写规则映射表，或 ② 写 `scripts/cvss_calculator.py`，让 Claude 只负责提取关键特征，分数由脚本按公式计算

**➡️ 由此引出追问讨论（未计分，深化理解）**：

> **我的质疑**：穷举映射表方案不完美——同为"文件上传漏洞"，能传 JSP（可致 RCE）与仅能传 TXT（信息泄露）风险等级天差地别，规则表无法覆盖这种语义判断。

> **讨论结论**：
> 
> - 该质疑成立，纯规则表无法覆盖依赖"上下文语义理解"的判断（如文件类型能否在当前服务器环境被解析执行）
> - CVSS 的真正设计思路是把"整体打分"拆解成 **8 个独立、离散、可枚举的子维度**（如 Attack Vector 只有 Network/Adjacent/Local/Physical 几个选项），LLM 只需回答"是/否"或选择离散档位这类**窄问题**，波动性大幅降低
> - 子判断完成后，**用确定性脚本公式聚合**成最终分数（这一步 100% 可脚本化）
> - **核心结论**：无法让"语义丰富的判断"变成纯规则查表，但可以把它**收窄成小粒度的分类问题**，再用脚本做确定性聚合——LLM 推理没有被消除，而是被限制在更窄、更可控的判断范围内

### 第5题｜难点收官题

**题目**：什么样的任务步骤"值得/能够"被转化为确定性脚本？什么样的任务"天然无法"脚本化，只能依赖 LLM 推理？请分别举例。

**我的回答**：

> 例如 `weather-fetcher` 这种，明确知道访问 url、api key/cookie、属性，返回的数据也是结构化和确定的，可以使用脚本实现；如果问题是不固定的/抽象的，返回的结果也是不确定的，则需要 LLM 推理，例如写策划方案、总结报告等

**反馈：✅ 正确，9/10**

- ✔️ `weather-fetcher` 例子精准：输入确定 + 输出结构确定 → 天然适合脚本化
- ✔️ "写方案/总结报告"作为开放式创作任务的例子方向正确
- 🔻 **扣分点**：仅举了"纯脚本"vs"纯开放推理"两个极端案例，未触及第4题讨论中挖出的更深规律——大量真实任务是**"LLM做窄粒度判断 + 脚本做确定性聚合"的混合型**
- **补充案例（招聘简历筛选）**：
  - 纯脚本：工作年限≥3年、是否含某证书关键词 → 正则/脚本直接判断
  - 纯LLM：判断"项目经历描述是否体现真实技术深度" → 依赖语义理解，无法穷举规则
  - **混合型（真实系统常用做法）**：把简历拆成若干"是否具备XX能力"的离散子问题（LLM判断"有/没有/不确定"），再用脚本按权重公式聚合成总分——与 CVSS 拆解思路完全一致

**核心规律**：判断任务能否脚本化，关键看**输入输出空间是否有限且可枚举**。

- 空间有限（文件后缀判断、CVSS 8个固定字段）→ 可脚本化，即使中间有 LLM 判断也是"有限选项里选一个"，波动小
- 空间无限开放（单一开放问题如"这份方案写得好不好"）→ 只能靠 LLM 整体推理，波动大
- **好的 Skill 设计 = 把"无限开放的大问题"拆解成"一串有限空间的小问题"，再用脚本聚合**

**总分：36/50，正确率 72%**（得分呈明显上升趋势）

### ✅ 掌握良好的知识点

- Skill 的真实文件架构（SKILL.md + scripts/ + examples.md）与渐进式加载原理，理解深度超出原文
- Agent 与 Skill 的调用关系（独立文件 + 按需触发，而非内容合并）
- 确定性脚本化的边界条件：**"拆解成有限选项子问题 + 脚本聚合"**这一核心规律（本次学习最大收获，来自第4题的深入辩论）

### ⚠️ 薄弱知识点（建议复习方向）

1. **"一致性(consistency)"与"正确性(correctness)"的区分**——Agent/Skill 保证的是方法统一，不是结果必然正确，需单独强化记忆
2. **多对多复用关系的真实案例**——建议查找 1-2 个"同一 Skill 被多个 Agent 复用"的实际项目案例加深印象

### 🧠 一句话记忆法

**Agent 是"岗位说明书"，Skill 是"操作手册"，两者保证的是"同一件事每次都用同一种方法做"，而不是"这件事做得对不对"——就像餐厅有标准化 SOP 不代表厨师厨艺一定高超，但至少保证口味不会忽好忽坏。**
