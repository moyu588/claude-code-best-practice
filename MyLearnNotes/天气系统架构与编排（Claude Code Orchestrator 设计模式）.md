## 一、知识点大纲

📌 **核心知识点**

1. **三层编排架构**：Command（调度）→ Agent（领域推理）→ Skill（纯执行）
2. **职责分离原则**：Orchestrator 只负责调度、把关、验证，不直接执行任务
3. **双重权限约束机制**：硬约束（`allowed-tools` 限制物理能力）+ 软约束（文字禁令约束执行逻辑）
4. **最小权限原则**：破坏性操作（如 Write）收敛到专门 Skill，降低误操作/安全风险
5. **Fail-closed 工作流逻辑**：每步严格依赖上一步"经过校验"的产出，校验动作本身不可被绕过，即使数据来源发生变化（如引入缓存）
6. **透明化封装（transparent）**：技术语境下"透明"=对上层不可感知，与日常语义正好相反
7. **Hook 双层映射机制**：主 session 层 vs 子 Agent 层，事件驱动声音反馈
8. **扩展模式**：新增功能需同步修改 Workflow、Execution Contract、Output Summary 三处

🔑 **关键概念**

| 概念                       | 说明                                |
| ------------------------ | --------------------------------- |
| Execution Contract（执行契约） | 强制路径确定性，防止绕过/模拟/时序错乱              |
| allowed-tools（工具白名单）     | 按"类别"而非"具体名称"授权                   |
| Skill 两种加载模式             | 预加载（Agent Skill）vs 主动调用（独立 Skill） |
| Fail-closed（默认失败关闭）      | 失败即停，禁止用默认值/猜测数据顶替                |

## 二、架构设计详解

### 2.1 三层结构与职责边界

```
Command（调度/把关/验证）
    │
    ▼
Agent（领域推理，如 weather-agent 内置 fetcher）
    │
    ▼
Skill（纯执行动作，如 weather-svg-creator）
```

- **解耦可扩展**：独立 Skill 可单独重构而不影响 Agent 内部逻辑
- **最小权限原则**：三层各自都有硬约束（禁止调用外部工具、禁止跳过 Skill）和软约束（满足条件才能进入下一步），权限层层收紧而非集中一处

### 2.2 层级归属易混淆点

| 组件                    | 触发方               | 层级归属           | 权限判断                  |
| --------------------- | ----------------- | -------------- | --------------------- |
| `weather-fetcher`     | Agent 内部触发        | Agent 层        | 统一走 Skill 工具入口        |
| `weather-svg-creator` | Orchestrator 直接触发 | Orchestrator 层 | 统一走 Skill 工具入口，权限判断一致 |

⚠️ **易错点**：两者触发路径不同，但因为都走同一个 Skill 接口，权限判断结果一致——不能只看"都是skill"这个表面结论，要理解"skill统一走同一接口"这个底层机制。

## 三、Fail-closed 原则的深层理解

### 3.1 "伪造数据"比"完全失败"更危险（核心共识）

| 场景         | 后果                            | 隐蔽性             |
| ---------- | ----------------------------- | --------------- |
| 完全不执行/报错   | 结果异常明显，系统能识别，直接触发 fail-closed | 早期即被拦截          |
| **伪造模拟数据** | 结果**看起来正常**，一路顺畅传递到后续步骤       | **只能靠人工核查才能发现** |

🎯 **共识**：伪造数据本质上比"没有数据"更糟，因为它**绕过了系统本该有的失败提示机制**，属于"隐性失败"——这是 fail-closed guardrail 存在的底层原因，而非单纯的技术限制。

### 3.2 Fail-closed 不等于禁止变化

> **"Fail-closed"是校验不能被跳过，不是数据来源不能变。**

以缓存功能为例：

- **错误方案**：Orchestrator 自己做缓存查询，自己校验缓存数据是否合理 → 让 Orchestrator 承担了不属于它的判断逻辑，一旦校验写得不严谨，Fail-closed 保证就有漏洞
- **正确方案**：缓存逻辑完全封装进 weather-agent 内部，Orchestrator 每次调用得到的都是"已校验"的结果，**感知不到是否命中缓存**

## 四、术语陷阱："透明"的真实含义

⚠️ **易混淆点**：日常语义"透明"= 看得清楚；计算机领域"透明"= **隐身、感知不到**（类比透明代理、GC 对开发者透明）。

> 缓存对编排层透明，意思是"Orchestrator 完全不知道、也不需要知道缓存是否存在"

**思维校正点**：遇到"需要加新功能（如缓存）"时，第一反应容易是"在当前层加逻辑处理它"，而不是先问**"这个逻辑该下沉到哪一层，让上层保持无感"**。

## 五、模型强弱选择的场景化逻辑

| 观点                     | 结论                                                                        |
| ---------------------- | ------------------------------------------------------------------------- |
| 预设：Orchestrator 必须用弱模型 | ❌ 非架构上的必要条件                                                               |
| 修正后：弱模型只是"够用即可"的成本效率选择 | 预算无限时，强模型不会造成质量损失                                                         |
| **反直觉点**               | 在"严格按流程执行、不许自由发挥"的场景下，强模型有时因"自作聪明"（跳步/加解释/改格式）反而更不可控——弱模型的"死板"在流程控制场景中是优点 |

## 六、Hook 双层映射机制

| 层级                                   | 映射表                    | 触发场景                 |
| ------------------------------------ | ---------------------- | -------------------- |
| 主流程感知层（Command 视角，"调用Agent"这个工具失败了）  | `HOOK_SOUND_MAP`       | `PostToolUseFailure` |
| 子 Agent 自身生命周期层（Agent 走到了终点，即便是失败终点） | `AGENT_HOOK_SOUND_MAP` | `SubagentStop`       |

⚠️ **易错点**：容易把 `PostToolUseFailure` 误归到 `AGENT_HOOK_SOUND_MAP`，或忽略子 Agent 失败时也会正常触发 `SubagentStop`（失败不等于没有终点事件）。

⚠️ **不确定性声明**：此映射关系基于逻辑推理沉淀，**未经 hooks.py 完整源码逐行核实**，建议对照源码确认。

## 七、系统整体设计哲学

1. **架构清晰**：分层调度，职责解耦，便于扩展
2. **最小权限原则**：多层硬/软约束限制每一层能做什么
3. **Fail-closed**：失败立即停止并告警，不允许"带病运行"
4. **可观测性/可审计**（延伸维度）：Hook 事件驱动的声音反馈机制让每个生命周期节点的状态变化都能被实时感知

## 八、总结评估

### ✅ 已扎实掌握

- 三层架构的职责划分与解耦逻辑，能准确判断"新功能该放哪一层"
- 禁止事项背后的设计意图（防绕过/防模拟/防时序错乱）
- Fail-closed 原理，能主动推理出"伪造数据比报错更危险"这一深层逻辑
- 依赖关系的业务直觉强，能主动质疑需求本身是否合理（如模型强弱选择）
- 系统整体设计哲学的归纳提炼能力

### ⚠️ 薄弱项

- 回答容易只覆盖"结论"，缺少"机制链条"的完整推导
- 多角度问题容易遗漏，倾向于挑最直觉的一个深入回答，其他角度需提醒才补全
- Hook 双层映射表的具体事件归属容易混淆，复习方向：找到 `hooks.py` 源码逐条核对

### 🎯 反复澄清才达成的共识（最有价值部分）

1. 伪造数据的危害性 > 完全失败，因为它绕过了系统的失败提示机制，属于"隐性失败"
2. "透明"是隐身而非看清楚——术语陷阱需牢记
3. 模型选择不是教条式必须，而是场景化的效率权衡
4. Agent 失败场景下，主 session 层和子 Agent 层各自留下的"痕迹"是互补而非替代关系

## 九、一句话记忆法合集

> **架构定位**："Orchestrator 是交通指挥，不是司机——它只看红绿灯（校验通过与否）放不放行，不摸方向盘（不直接执行任何具体动作）。"

> **术语与原则**："透明"是隐身，不是看清楚；"Fail-closed"是校验不能被跳过，不是数据来源不能变。
